How one request becomes one trace

Three views of the same minikube lab: the full path a request and its telemetry take through the mesh, the propagator bug that split every trace in two, and the one-file patch — the Dockerfile.productpage-patched currently open — that puts it back together.

1 — The stack, two paths through it

Every request follows the same route Envoy sidecars route it along (solid). Alongside it, each sidecar and the app itself independently ship spans and metrics to the observability namespace (dashed / dotted) — a separate plane that Kiali and Jaeger read back from, never the request path itself.

2 — Why spans didn't join into one trace

Getting Fig. 1's dashed path working was step one. It produced traces — but every one of them arrived in Jaeger as two disconnected trees: Envoy's hops correctly chained together, and the app's own Flask span sat off to the side under a different trace ID. Same request, same headers, two identities. Here's the mechanism, before and after the fix in productpage_patched.py.

3 — Where the open file fits

Dockerfile.productpage-patched is the delivery mechanism for Fig. 2's fix — it doesn't contain the patch itself, it bakes the already-edited source file over the stock image.

Port The Instrumentation CR must point at :4318 (OTLP/HTTP), not :4317 (gRPC) — Python's auto-instrumentation defaults to HTTP, and pointing it at the gRPC port silently fails every export with a 415.
Not the same bug Removing the inject-python annotation entirely (Step 10 of the runbook) does not break Envoy-to-Envoy correlation on this stack — productpage.py separately copies the raw traceparent/tracestate header values by hand in getForwardHeaders(), independent of the OTel SDK. Only the app's own span joining the chain depends on Fig. 2's fix.
